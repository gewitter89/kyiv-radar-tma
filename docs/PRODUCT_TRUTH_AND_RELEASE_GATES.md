# Київ Радар — правила справжнього продукту та журнал рішень

Дата початку: 17.11.2026. Цей документ — тривалі правила для наступних розробників і ШІ-агентів. Мета: реальний сервіс пошуку житла, а не імітація користувачів, квартир або перевірок.

## Правило №1: факти, які має право показати застосунок

| Твердження в інтерфейсі | Джерело доказу | Якщо доказу немає |
| --- | --- | --- |
| Власник підтверджений | Окрема приватна перевірка права власності, модератор, дата | «Власника не перевірено» |
| Квартира актуальна | Незалежне підтвердження наявності з датою | «Наявність не перевірена» |
| Контакт перевірений | Перевірка конкретного каналу зв'язку | «Контакт не перевірено» або «Контакт недоступний» |
| 0% комісії | Самостійне підтвердження умов, окреме від особи власника | «Комісія уточнюється» |
| Генератор / GPON | Заява автора оголошення або окремий доказ | «Заявлено»; **GPON не є генератором** |
| Точна адреса / кілометри | Незалежно перевірені координати і дозвіл на їх показ | Район без точних міток, без відстані |
| «Нове оголошення» | Достовірна дата публікації в джерелі, не дата імпорту | Не показувати «нове» |
| Доставлено контакт у Telegram | Підтвердження успішної відповіді сервера | Помилка, пояснення причини й відновлення |

Жодне з цих підтверджень не переноситься автоматично на інші твердження. Результат антидубль-алгоритму — лише кандидат для людини, не «шахрай».

## Правило №2: без вигаданих доказів життя сервісу

Заборонено публікувати вигадані квартири, контакти, користувачів, власників, відгуки, лайки, перегляди, успішні оренди, «покупців онлайн», таймери попиту, штучний дефіцит, фальшиву економію, невідомі дати перевірки та імітовані переписки. Демонстраційні записи — лише в ізольованому тестовому середовищі з чітким маркуванням.

Дизайн: звичайна природна українська мова; факти й одна зрозуміла дія на екрані; тиха типографіка, доступні натискання, без надмірних сяючих ефектів, зайвих емодзі, «Apple-style» як рекламної обіцянки, штучних testimonial або автоматично згенерованих псевдолюдей. Дозволено використовувати ШІ як робочий інструмент, але не видавати його за перевірку людиною. Кожну критичну помилку формулювати конкретно (404 немає контакту; 429 ліміт; 401 Telegram-авторизація; 502 доставка ботом).

## Правило №3: права на джерела та оновлення

- **Власні оголошення:** публікація лише після явно підтвердженого права подавати контакт/фото й рішення модератора; згода при поданні — ще не доказ власності.
- **OLX:** офіційний Partner API працює, зокрема, від імені авторизованого користувача через OAuth; це **не** дозвіл скопіювати все чуже портфоліо/фото. Див. https://developer.olx.ua/articles/partner-application-user та https://developer.olxgroup.com/faq
- **DIM.RIA:** перевірки DIM.RIA/позначки інспектора належать джерелу, а не автоматично нашому застосунку; дозвіл на републікацію слід погоджувати окремо. Див. https://dom.ria.com/uk/about-checks/ та https://developers.ria.com/
- **Telegram:** фронтенд передає підписаний initData на бекенд; авторизацію й права вирішує сервер, а не будь-який клієнтський прапорець. Див. https://core.telegram.org/bots/webapps
- Для 150 історичних імпортованих записів право на фото, актуальність і власники **не підтверджені**. Дата імпорту не є датою публікації або перевірки. Не вмикати автоматичні повідомлення/рекламу, не обіцяти 0% комісії.
- Дані для модератора, докази та контакти зберігати окремо від GitHub і відкритих артефактів. Права відкликання, скарги та видалення обов'язкові.

## Перевірюваний ланцюжок користувача

Орендар: відкрив → зрозумів рівень перевірки → обрав район/бюджет → переглянув одну картку → перевірив джерело → запросив контакт → отримав **або** конкретне пояснення відсутності → може поскаржитися.

Власник: відкрив через Telegram → підтвердив права на фото і контакт → подав квартиру → побачив реальну відповідь сервера → модератор переглянув заявку → рішення з журналом → може виправити/відкликати.

До публічних обіцянок потрібні 3–5 справжніх власників (добровільна згода), реальне ручне E2E на iPhone/Android, а потім 10–20 тестувальників. Жодні «готово» чи «перевірено» не ставити за моки.

## Журнал технічних рішень

- **v1.16 / PR #27:** аудит кандидатів у дублікати і provenance; не автоматичний антифрод. 150 імпортованих записів не стають перевіреними.
- **v1.17 / PR #28:** приватна офлайн-черга перевірок, усі статуси спочатку «not_reviewed», жодної зміни production API.
- **v1.18 / PR #29 (під час розробки):** прибрати хибні твердження про генератор, безпосередній контакт, підтверджену ціну та точну відстань; окремо пояснювати 401/404/429/502. Не оголошувати випущеним до CI та GitHub Pages.
- **v1.18 — доказовість контактів:** виявлено 150 маскованих номерів в імпортованих JSON/HTML за відсутності підтверджених контактів. Маски з історичних даних прибрані, а клієнт ігнорує `phoneMasked` для запису без `contactVerified`; статус «Контакт не підтверджено». Це не доводить, що на оригінальних майданчиках номерів немає — лише що наш сервіс не може підтвердити їх доступність. Зв'язок треба перевірити через власника з добровільною згодою.

- **v1.19 / source-first (робота через PR):** жодна з 150 імпортованих пропозицій не має підтвердженого контакту у нашому каталозі, проте кожна містить оригінальне посилання OLX/DIM.RIA. Першу дію змінено на **«Перевірити на OLX/DIM.RIA»** (лише для перевіреної адреси джерела), а запит у Telegram не відправляємо для непідтверджених імпортів. Для власних пропозицій і окремо підтверджених контактів зберігається серверний Telegram-сценарій. **Не означає**, що 150 джерел є актуальними або маємо право передруку фото. Не оголошувати production-релізом до проходження CI і Pages.

- **v1.20 (окремий PR):** у всіх 150 історичних імпортованих записах були значення `metro` та точні `walkMin`, але не було незалежно підтвердженої геолокації. Тому їх **прибрано** з публічного JSON/вбудованого fallback; клієнт також відкидає неперевірені значення з API. Пошук за текстом первинної назви лишається можливим; про маршрут/станцію запитуємо в оригінальному джерелі або перевіряємо відтворюваним маршрутом після згоди власника. Підтверджені локації та власні оголошення не позбавляємо цих полів. Зміна не підтверджує інших географічних, медійних чи фінансових даних і не зачіпає VPS.

## V1.21 — реальна подача власника та декларація прав

- **Виявлений недолік v1.20:** форма приймала `llRights` тільки під час остаточної подачі, але могла передавати приватні фотографії на сервер раніше. Це не дозволяє робити висновок про отримані права.
- **UI:** чекбокс декларації прав перенесено **перед** фотозавантаженням. Без явної дії власника `FileReader` і `fetch(upload_photos)` не запускаються. Форма не обіцяє автоматичної публікації.
- **Backend (окреме контрольоване розгортання):** `/api/landlords/upload_photos` вимагає `rightsConfirmed=true` і `consentVersion=owner-rights-2026-11-v1` **до читання/збереження фото**. `/api/landlords/submit` теж відхиляє невідому версію; обидва дії потребують чинного Telegram initData.
- **Audit:** у приватній SQLite `landlord_consent_receipts` зберігаються тільки `submission_id`, версія, SHA-256 незмінного тексту декларації і дата. Це **доказ зафіксованої самодекларації**, а не доказ власності, ліцензії на фото, актуальності або перевіреного контакту. Реальні перевірки — окремі рішення модератора.
- **Не розміщувати секрети або документи у GitHub:** усі особисті контакти, фото, документальні докази та заявки живуть виключно у приватному сховищі на VPS після операторської перевірки конфігурації.
- **Release sequence:** CI green; GitHub Pages static frontend можна випустити окремо. **Не стверджувати, що сервер захищений новим контрактом**, доки не підтверджено точний production import path, backup SQLite/WAL, Caddy config + ліміт 33 MiB, нову схему, повторний контрольований API deploy і живий тест. Старий токен не міняти без окремого дозволу; ризик #7 залишається.
- **Пілот:** реальні 3–5 власників лише після сумісного API: HEIC/JPG → дозвіл → приватний upload → `pending_review` → людська модерація → перевірка контакту → видалення/скарга. Немає тестових заявок у production.
- **Rollback:** static: повернути попередній Pages-коміт, якщо ламається UX; API: зупинка нового розгортання та повернення перевіреної копії коду після backup. Не відновлювати базу без окремої валідації журналу WAL.

## Постійні стоп-умови

Не змішувати функціональне «API працює» з «пропозиція існує в житті». Не показувати необґрунтовані точні мітки і фінансові переваги. Не створювати удавані верифікації. Не проводити зміни токена або конфігурації чужих VPS-сервісів без окремого дозволу й координованого плану. Відомий ризик старого Telegram-токена лишається відкритим у Issue #7.
