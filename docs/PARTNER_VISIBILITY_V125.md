# Київ Радар v1.25 — partner visibility (staging feature, not a live feed)

## Що працює в коді

Після `v1.24` приватна БД `source_rights` містить права на джерело,
а `inventory` — статус перевірки елемента. `server/partner_visibility.py`
підключається до єдиного `load_effective_deals()`, яким користуються
`GET /api/deals`, `GET /api/health` і перевірка `/api/send_contact`.

Тільки явно позначений `partner:<source_key>` із одночасними
`partnerSourceKey` та `partnerExternalId` може проходити партнерський gate.
Для такого запису на *кожному серверному читанні* потрібно:

1. Окремий приватний reviewer-підтверджений факт доступності (`actualityConfirmed`),
   не прапорець із завантаженого файла.
2. Приватна БД, яка доступна тільки для читання через
   `KYIV_RADAR_PRIVATE_PARTNER_DB`.
3. Договір джерела `source_rights`: `active`, строк дії не завершився,
   збережений scope fingerprint.
4. Запис `inventory`, зв'язаний за `(source, external_id)`, в статусі
   `approved`, не `possible_withdrawn`, та той самий canonical source URL.

При відсутності будь-якої умови partner-card не включається до API.
Поля `partnerSourceKey`, `partnerExternalId`, reviewer, приватні докази,
телефон і ім'я власника не експортуються до API.

**Це не достатня ліцензія для автопублікації!** Наявність запису в приватній
БД не підтверджує права на фото, авторський опис, телефон чи конкретні
об'єкти. Оператор повинен окремо перевірити партнерський договір, право на
використання потрібних полів і розміщувати записи в публічному каталозі
тільки після дозволеного workflow.

## Фронтенд і ризик резервної копії

`index.html` при недоступності API користується статичними копіями
`data/deals.json` / `KYIV_DEALS_INIT`. Для partner-marked записів
додано fail-closed `staticCatalogWithoutPartners()`: вони ніколи не
відновлюються з цих копій навіть якщо API недоступне. CI також перевіряє,
що partner-marked даних у самих публічних копіях немає.

**Важливе обмеження:** 150 історичних OLX/DIM.RIA карток — окремий legacy
каталог, без partnerSourceKey і без ліцензійних підтверджень; цей PR їх
автоматично не прибирає, не називає перевіреними й не перетворює на
партнерське джерело. При потребі приховати весь legacy каталог потрібен
окремий погоджений release, зміни fallback і оновлення UX-тестів.

## Налаштування (секретів у GitHub не зберігати)

```bash
# Приклад тільки шляху до приватної бази, без API-ключів.
KYIV_RADAR_PRIVATE_PARTNER_DB=/secure/radar/inventory.sqlite
```

За замовчуванням змінна **не задана**, отже всі partner-marked записи
залишаються невидимими. Ніяких нових live-джерел не активується.

## Тести та release gates

- Без DB / неправильної DB / без схеми / без запису / без підтвердження
  актуальності / без approval => 0 партнерських карток.
- Зміна URL, невідповідність partner source/id => 0.
- Revoke або expiry => зникає з API на *наступному запиті*, а не після
  перезбирання статичних даних.
- `send_contact` та `health` використовують той же gated list.
- Статичні offline-копії ніколи не містять partner-marked об'єктів.
- Усі зміни потребують зеленого CI та owner-controlled release.
- Старий токен, VPS, production secrets, бот і live data НЕ змінювати
  без окремого рішення.

## Що ще НЕ реалізовано

- Строгий publisher з доказами дозволу для конкретного поля (фото/опис/
  геодані/комісія) й журналом згоди та відкликання.
- Контроль інших можливих surface: CDN/SEO/social-preview/Telegram алерти,
  кеш мобільного браузера, відкриті вкладки. Немає гарантії миттєвого
  видалення із вже відкритого браузера, навіть якщо API відповідає 0.
- Сумісність із різними партнерами XML/YRL за індивідуальним mapping.
- Юридично підтверджене підключення реальних фідів і незалежна перевірка
  150 legacy карток.
