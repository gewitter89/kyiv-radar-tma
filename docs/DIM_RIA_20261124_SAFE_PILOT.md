Компанія вимагає актуальності оголошень, деактивації знятих, актуального посилання на DIM.RIA, забороняє зберігання **і показ** контактів користувачів, просить посилання на наш ресурс після запуску та обробку звернень про видалення.

Екран з прямим посиланням на джерело (без наших копій фото/контактів) — найбезпечніший ранній формат, але він також потребує підтвердження прав на конкретні метадані.

## Бюджет та економіка запитів

У листі зазначено можливість **100 або 1 000 безкоштовних запитів протягом 30 днів** залежно від наданого доступу. Таблиця тарифів може відображати 1 000 / 30 за годину, але **це не доказ, що конкретний акаунт отримав 1 000**.

Поточний `scripts/dim_ria_discovery.py`:
- без `--execute`: 0 API calls;
- з `--execute`: приватний операторський дозвіл, ключ тільки з `DIM_RIA_API_KEY`, не в URL репозиторію;
- спільна SQLite квота (усі запуски на цьому операторському DB), **не більше 30 запитів за ковзні 60 хв і 100 за ковзні 30 днів**, включно із зарезервованими timeout/error/429;
- підтримка старого ledger консервативна: записи без точної дати рахуються за **всіма** потенційно релевантними годинними та місячними bucket, без скидання лічильника 1 числа;
- ніяких публікацій з цього скрипта, він збирає лише ID у приватній БД.

**Поточна захищена квота діє лише на discovery через цей модуль**. Наявні сторонні клієнти, окремі API script / keys, зовнішні запити або billing не контролюються цим лічильником. Поки немає централізованого quota gate для search + info та підтверджених прав — **заборонено запускати окремий info-адаптер на живому ключі**.

Розрахунок прикладу для пілота (не запуск): 1 пошуковий запит кожні 3 дні = приблизно 10 / 30 днів; 2 перевірки деталей на день = 60 / 30 днів; разом **70 запитів**, резерв **30** до найбільш консервативного 100-call cap. Це не масштабована синхронізація всього ринку; кількість підтримуваних актуальних карток залежить від refresh SLA та фактичного пакета.

## Release gates перед публічними картками

1. Оператор отримує API key, підтверджує з кабінету точний безкоштовний пакет, expiry, reset semantics та кількість доступних запитів. Без ключа/права/за замовчуванням — 0 мережевих запитів.
2. Отримує від DIM.RIA письмове підтвердження scope метаданих і attribution (включно із питаннями фото/опису) та визначає retention/deletion.
3. Створює централізований encrypted/private API-side quota ledger для search + info; забороняє client-side ключі, логування URL із `api_key`, повторний обхід ліміту через інші процеси.
4. Підтверджує точний provider state mapping (active/deactivated, 404/410, часткова search pagination) на офіційних fixtures; **не вважає відсутність у частковому search підтвердженим видаленням**.
5. Приватно проганяє кілька синтетичних та реальних дозволених кейсів. Deactivated / staleness / API unavailable → картка не заявляється як активна. Не підміняти відсутність відповіді старими 150 картками.
6. Кожній дозволеній картці — явне джерело, посилання саме на лот, відома дата перевірки з істинним значенням, скарга/видалення; без телефону, ім'я продавця, фальшивих `verified` badges або скопійованих медіа.
7. Перевірити GitHub Pages public HTML/JSON на старі 150 непідтверджених лотів (#55), API fallback (#52), кеші, Telegram alerts і CORS. Live production тільки окремим захищеним deploy після green CI та реальної E2E-перевірки.
8. Передати DIM.RIA URL сервісу після публічного запуску та контакт для takedown, як вони попросили.

## UI: якісний, але чесний продукт

- Чисті картки: **тип угоди / район / ціна / площа / кімнати**, відоме походження, час останньої підтвердженої перевірки.
- Без дозволених фото — власний нейтральний placeholder з лаконічним візерунком і коректним alt, не фальшива фотографія нерухомості.
- CTA «Переглянути на DIM.RIA» веде на перевірений офіційний лот, не імітує «зателефонувати власнику».
- Чіткі стани: **є підтверджені поточні пропозиції**, **немає придатних лотів**, **дані тимчасово недоступні**.
- Ніякого public reach / "150 квартир" / "без комісії" без доказу.

Усі показники користувачів, договори, ліцензії та витрати мають відображати **фактичні**, а не синтетичні дані.
