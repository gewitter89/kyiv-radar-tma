# Київ Радар — інтеграційний реліз v1.32: інвентар, право публікації, відкат

> **Статус:** draft PR #54, НЕ production deploy. Стан репозиторію, тестів і VPS треба перевіряти за конкретним SHA перед кожною зміною. Успішна збірка чи GitHub PR не доводить оновлення VPS або GitHub Pages. Ніяких нових API-платежів, бот-токенів чи автоматичного імпорту чужих оголошень.

## Що реалізовано у draft PR #54

- Публічні `index.html` і `data/deals.json` містять `[]` замість 150 історичних імпортів; це не стирає старі коміти, форки, кеші CDN чи раніше скачані копії.
- Замість живих історичних даних із незалежно непідтвердженими правами CI створює **150 суто синтетичних тестових квартир** у тимчасовому checkout; записи позначені `fixtureOnly`, не стають юридично дозволеними об'єктами і не мають реальних фото.
- `scripts/check_public_distribution.py` перевіряє публічні HTML/JSON **до** створення синтетичних записів. Регресійні тести не повинні дозволяти тестовому генератору пройти у deploy artifact.
- Публічний HTTP(S) frontend у разі помилки API показує чесну помилку і «Спробувати знову» замість старого каталогу; `file://` використовується лише для локального QA.
- Серверний спільний `load_effective_deals` відкидає старі OLX/DIM.RIA-імпорти (незалежно від статусу `actualityConfirmed`). Прямі заявки допускаються лише з `source = "Київ Радар (Пряма заявка)"`, позитивним `submission_id` та `moderationStatus = approved`. Партнери допускаються лише після окремого серверного `enforce_partner_visibility` із приватною перевіркою прав та чинною ревокацією.
- `GET /api/deals`, `GET /api/health` та `POST /api/send_contact` використовують один серверний фільтр; перевірка браузера не є єдиним захистом.
- Stable favorites, мобільні UI-тести і статус невдалого каталогу зібрані з PR #50, #51, #53 в одному інтеграційному PR #54.

## Безпечна послідовність випуску

1. **Preflight тільки на читання:** зберегти HEAD та running SHAs для Pages/API, перевірити `/api/health` і `/api/deals`, Caddy/version, роботу бота, права на інвентар. Не вважати успішний frontend build доказом продакшену.
2. **Private backup**: консистентна SQLite Online Backup API / WAL, медіа, contacts vault, чинні налаштування сервісів і код без доступу сторонніх. Не зберігати backup у GitHub чи логах.
3. **Staging:** backend з фільтром прав + frontend; жодних реальних сторонніх фото та контактів, усі API-запити у тестах перехоплені.
4. **Coordinated cutover:** якщо backend/bot на спільній БД чи з імпортами, узгоджено зупинити саме відповідні writers, не торкатися KyivPulse або Vudstoria; визначити точні `ExecStart`, Python imports, cwd. Нову базу/схему не мігрувати без окремого узгодженого плану.
5. **Frontend Pages:** лише після сумісного backend, перевірити фактичну публікацію конкретної ревізії; `main` commit сам по собі не доказ. Перевірити, що браузерне `200 + []` відповідає стану без дозволених об'єктів.
6. **Smoke + review:** оператор тестує один реальний, дозволений user journey; телефон/завантаження/модерація/скарга/контакт у Telegram без масового спаму, коректні дані без PII.
7. **Моніторинг:** 5xx, elapsed response, JSON validity, `count` і фільтр джерел, помилки браузера, стан підключення та скарги. `deals: []` = **немає інвентарю**, не API outage; оператор має отримати попередження, але не успіх supply.

## Відкат без повторної публікації чужих оголошень

- **Не відкочувати публічні файли до старої версії з 150 імпортами:** це відновить відомий ризик. Підготувати порожню fail-closed maintenance-build, яка не містить legacy inventory.
- Якщо API поганий, безпечна версія frontend показує `error`/retry і **не** підставляє старі лоти; backend не має розкривати raw private fields. Відкотити код тільки до **перевіреної privacy-safe** ревізії.
- Базу SQLite не замінювати через `cp` при активних процесах/WAL. Відновлення даних — окрема свідома процедура з відключенням всіх writers, валідованим snapshot і reconciliation нових заявок.
- Ніколи не обіцяти фіксований час відкату. Всі результати і SHA фіксувати без секретів.
